PENGATURAN RAILWAY
1. Pastikan service mempunyai domain publik HTTPS (Public Networking). Endpoint webhook: https://DOMAIN-RAILWAY-ANDA/webhooks/smscode
2. Pada Variables, tambahkan SMSCODE_WEBHOOK_URL dengan URL endpoint tersebut.
3. Tambahkan SMSCODE_WEBHOOK_SECRET dengan secret acak yang kuat. API token SMSCODE_API_TOKEN tetap yang sudah ada.
   Untuk membuat secret, gunakan Console Railway: node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
   Salin hasil ke SMSCODE_WEBHOOK_SECRET. Jangan bagikan secret/token atau masukkan .env ke GitHub.
4. Tunggu deployment terbaru aktif dengan Variables tersebut, lalu buka Console service dan jalankan:
   node smscode-webhook.js
   Perintah ini mendaftarkan URL dan secret ke SMSCode melalui PATCH /webhook, lalu menjalankan POST /webhook/test.
   Pesan sukses: Webhook SMSCode tersimpan dan tes HTTP 200 berhasil.
   Jika tes bukan 200, periksa domain publik, deployment, serta secret. Perintah dapat dijalankan ulang setelah memperbaikinya.
   Ulangi perintah jika domain atau secret berubah. Jangan mengubah Start Command Railway; tetap gunakan Start Command bot yang sudah ada.

CARA KERJA
Endpoint memeriksa X-Webhook-Signature sha256=HMAC(raw body, webhook_secret), menyimpan antrean sebelum memberi HTTP 200, dan memeriksa order terbaru lewat API token SMSCode.
Event order.otp_received/order.completed/order.expired/order.canceled memicu pembaruan order lokal dan pengiriman OTP/SMS ke DM pembeli sesuai order yang tercatat.
Payload webhook tidak dapat memilih pembeli, membuat order, memotong/mengisi saldo, atau memicu refund. Aturan refund bot yang sudah ada tetap berlaku.
Antrean gagal/DM tertutup dicoba ulang; notifikasi berulang tidak mengirim ulang kode yang sama. Antrean/notifikasi yang diterima disimpan di SQLite pada volume; entri webhook dibersihkan setelah 48 jam.
Polling 15 detik tetap berjalan sebagai cadangan karena SMSCode memakai timeout 3 detik tanpa retries. Tidak ada klaim pengiriman persis sekali bila proses mati di antara pengiriman DM dan pencatatan hasil.
Validasi: 21 pengujian operasi dan webhook lokal lulus, termasuk signature, duplikat, restart, status terminal, SMS tanpa kode, revisi lama, dan konfigurasi/test API tiruan. Belum didaftarkan pada akun SMSCode pengguna atau diuji live.
Dokumentasi resmi: https://smscode.gg/docs (Webhook Notifications dan GET/PATCH/POST /webhook).

PAKET TERBARU — 7 FITUR TAMBAHAN DAN ADMIN LEBIH RAPI

CARA UPDATE DI IPHONE
1. Unduh dan ekstrak ZIP. Cadangkan database sebelum update melalui fasilitas backup/unduh Railway yang tersedia. Jangan menghapus volume /data.
2. Upload seluruh 16 file runtime .js di bawah ke folder utama repository GitHub (folder yang sama dengan package.json). Timpa file lama dan Commit changes. Pertahankan package.json/dependency yang sudah ada; tidak perlu npm baru.
index.js, admin.js, purchase-flow.js, payments.js, pricing.js, commerce.js,
direct-payments.js, operations.js, server-access.js, staff.js, navigation.js,
store-features.js, efficiency.js, midtrans.js, coupons.js, shop-tools.js.
Dua file baru adalah coupons.js dan shop-tools.js. File *.test.js hanya untuk pengujian, tidak wajib dipasang untuk menjalankan bot.
3. Jangan upload .env, API key, token, shop.db, database backup atau bukti pribadi ke GitHub. .env.example hanya contoh konfigurasi.
4. Pertahankan Variables gateway, token, owner/admin yang sudah benar. Volume harus tetap terpasang /data dan database berada di volume (misalnya DB_PATH=/data/shop.db). Tidak ada Variables wajib baru untuk fitur ini.
5. Tunggu deployment Railway sukses. Jalankan /shop dan /admin lagi agar menu baru muncul. Pesan lama tidak otomatis berubah semua.

MENU ADMIN — HANYA 5 KATEGORI
Toko: katalog provider, produk manual, harga jual, voucher.
Pembeli: daftar saldo, cari pembeli, tambah saldo, riwayat saldo manual, tiket bantuan.
Pembayaran: pengajuan manual, kasus perlu diperiksa, cek topup tertunda, riwayat isi saldo/QRIS beli, petunjuk manual.
Laporan: hari ini, bulan ini, biaya gateway aktual, ekspor CSV pada masing-masing laporan.
Sistem: izin server/admin, maintenance, backup owner, aktivitas admin, koneksi provider, peringatan saldo provider.

1. BACKUP DATABASE
Backup pertama saat bot aktif, kemudian sekali per hari WIB; penjadwal memeriksa setiap jam. Tujuh salinan terbaru disimpan di folder backups di samping database, misalnya /data/backups. Opsional BACKUP_DIR=/data/backups.
Sistem > Backup (Owner): jalankan sekarang, aktif/nonaktif jadwal, unduh backup terakhir (maksimal 8 MB lewat Discord). Hanya owner dapat mengakses database lengkap. Admin tambahan tidak dapat mengunduhnya.
Backup di volume yang sama tetap hilang jika volume dihapus. Unduh dan simpan terpisah atau aktifkan backup volume Railway. Pastikan ruang volume cukup untuk database ditambah tujuh backup. Jangan bagikan database ke channel publik/GitHub.
Tidak ada tombol restore otomatis. Pemulihan dilakukan ketika bot berhenti, setelah menyalin database saat ini dan memeriksa semua pembayaran yang terjadi sesudah tanggal backup; pemulihan sembarangan bisa mengulang pencatatan saldo.

2. CEK PEMBAYARAN TERTUNDA OTOMATIS
Topup diperiksa maksimal 5 tagihan per batch setiap 30 detik. Pembelian QRIS memiliki pemeriksaan tersendiri. Saldo/pesanan hanya diproses oleh pemeriksaan gateway resmi yang sudah ada. Tidak membuat tagihan pengganti saat timeout/hasil belum pasti. Tombol Pembayaran > Cek Topup Tertunda menjalankan satu batch tambahan. Tagihan lama mengikuti gateway dan mode saat dibuat.
Notifikasi isi saldo sukses dikirim lewat DM; jika DM tertutup, pembeli tetap dapat memeriksa Saldo. QRIS tetap memerlukan merchant dan konfigurasi gateway yang valid.

3. TIKET BANTUAN
Pembeli: Bantuan > Buat Tiket Bantuan / Tiket Saya. Referensi pesanan opsional hanya boleh milik pembeli tersebut. Maksimal 3 tiket terbuka per pembeli, pesan maksimal 1000 karakter.
Admin: Pembeli > Tiket Bantuan, pilih tiket untuk membalas atau menutup dengan alasan. Tampilan menampilkan 5 pesan terakhir dengan ringkasan jika panjang; teks lengkap tetap disimpan. Notifikasi DM dicoba ulang jika gagal. Semua percakapan menu pribadi.

4. RIWAYAT AKTIVITAS ADMIN
Sistem > Aktivitas Admin menggabungkan tindakan toko, saldo manual, resolusi pembayaran, pengaturan, akses admin/server, voucher, tiket, backup dan biaya gateway. Tampilan per 5 kegiatan dan pesan panjang diringkas. Riwayat ini pencatatan aplikasi, bukan rekaman yang tahan perubahan oleh pemilik database.

5. LAPORAN BIAYA DAN CSV
Laporan hari/bulan memakai WIB, menampilkan penjualan setelah diskon, diskon voucher, refund, penjualan net, biaya provider tercatat, biaya gateway tercatat dan biaya yang belum tercatat. Ekspor CSV berupa ringkasan periode.
Angka selisih bersifat sementara, belum termasuk hosting/biaya lain. Biaya gateway diakui pada periode pembayaran seluruh topup/pembelian; bukan alokasi biaya per pesanan. Refund ditampilkan menurut tanggal order. Transaksi lama tanpa paid_at memakai tanggal tagihan.
Biaya Midtrans yang belum diberikan API ditandai belum tercatat, bukan dianggap gratis. Masukkan biaya merchant aktual dari mutasi di Laporan > Catat Biaya Gateway. Isi 0 hanya bila memang bebas biaya. Biaya TriPay tercatat mengikuti informasi gateway; koreksi manual disertai catatan.

6. NOTIFIKASI STOK FAVORIT
Beli OTP > Favorit Saya > pilih favorit > Notifikasi Stok On/Off. Notifikasi DM dikirim saat stok kombinasi aplikasi/negara/operator tersedia; tidak memesan nomor otomatis. Jika stok sudah ada saat diaktifkan, notifikasi pertama tetap dikirim.
Maksimal 5 favorit diperiksa per menit secara bergilir; cache katalog dan jumlah pelanggan dapat menambah waktu tunggu. Pemberitahuan berikutnya dikirim setelah stok sempat kosong lalu tersedia lagi. Jika DM ditutup, pemberitahuan dicoba lagi.

7. VOUCHER DISKON RUPIAH
Toko > Voucher > Buat Voucher. Isi kode, diskon nominal rupiah, minimum pembelian, tanggal kedaluwarsa YYYY-MM-DD (sampai akhir hari WIB), dan batas total penggunaan. Setiap pembeli hanya sekali per kode. Tekan voucher pada daftar untuk menonaktifkan/mengaktifkan.
Pembeli memakai tombol Gunakan Voucher di konfirmasi produk, lalu membayar lewat saldo atau QRIS. Gunakan konfirmasi terbaru untuk melihat nominal setelah diskon. Diskon tidak boleh membuat harga di bawah biaya provider. Voucher divalidasi ulang saat pembayaran. QRIS minimal harga produk 1000 IDR; gunakan saldo untuk nominal lebih kecil.
Tagihan tertunda menahan kuota voucher. Kuota dilepas hanya setelah status tagihan tidak aktif yang sudah diverifikasi dan belum dibayar; timeout tidak melepas kuota. Pembatalan/refund pesanan mengembalikan harga yang benar-benar dibayar ke saldo bot, dan tidak mengembalikan hak voucher yang sudah dipakai.

PENGUJIAN
138 tes lokal lulus untuk fungsi baru dan seluruh fitur sebelumnya. Backup hasil tes berhasil dibuka kembali. Voucher saldo/QRIS, refund nominal diskon, kepemilikan tiket, peran admin/owner, retry pembayaran/DM, batas Discord, dan laporan WIB diuji. B. Refund ke Saldo: isi ID order jika ada, catatan pemeriksaan, dan ketik SUDAH DIPERIKSA. ID order yang sudah tercatat wajib dipakai. Jika masih aktif dan belum menerima OTP, bot membatalkan dan membaca ulang status sebelum refund. Order yang sudah menerima OTP/selesai ditolak untuk refund. Refund hanya harga produk ke SALDO BOT, bukan rekening pembayaran; biaya QRIS tidak termasuk. Penambahan saldo, perubahan status, dan catatan admin disimpan dalam satu transaksi database. Tagihan yang sudah diselesaikan tidak direfund atau dihubungkan lagi. Jika API/pembatalan bermasalah, tagihan tetap review, bukan membeli ulang. Ganti index.js, payments.js, direct-payments.js di GitHub pada folder yang sama dengan package.json. Modul admin.js, purchase-flow.js, pricing.js, commerce.js tetap diperlukan dari versi terakhir. Tidak perlu mengubah package.json. File .env.example adalah contoh, jangan menimpa Variables/token lama. Jangan commit .env atau API Key.
ZIP juga memuat seluruh modul versi terbaru dan file pengujian. Jika belum memasang versi admin/katalog/markup sebelumnya, gunakan seluruh delapan modul: index.js, admin.js, purchase-flow.js, payments.js, pricing.js, commerce.js, direct-payments.js, operations.js.
Tunggu deployment Railway terbaru berhasil, lalu buka /shop dan /admin baru. Pesan Discord lama tidak otomatis berubah.

VARIABEL RAILWAY UNTUK TRIPAY
TRIPAY_API_KEY = API Key merchant dari akun TriPay
TRIPAY_PRIVATE_KEY = Private Key merchant dari akun TriPay
TRIPAY_MERCHANT_CODE = kode merchant dari akun TriPay
TRIPAY_QRIS_CHANNEL = QRIS (atau kode QRISC / QRIS2 / QRIS_SHOPEEPAY yang aktif di merchant)
TRIPAY_IS_PRODUCTION = false untuk uji Sandbox; true untuk pembayaran nyata Production
Ketiga credential harus berasal dari merchant dan mode yang sama. Merchant serta channel QRIS harus aktif. Variabel MIDTRANS_* tidak digunakan oleh integrasi baru.

MENDAPATKAN CREDENTIAL DAN CALLBACK
Menurut dokumentasi TriPay:
Sandbox: API & Integrasi > Simulator > Merchant > Detail; aktifkan channel di Simulator > Merchant > Channel Pembayaran.
Production: Merchant > Opsi > Edit (letak label dapat mengikuti dashboard); channel di API & Integrasi > Merchant > Opsi > Atur Channel Pembayaran.
Isi callback default merchant yang sesuai mode dengan:
https://DOMAIN-BOT-KAMU/api/payments/tripay/callback
DOMAIN-BOT-KAMU adalah domain HTTPS publik service bot Railway, bukan alamat dashboard railway.com. Railway > service bot > Settings > Networking > Public Networking > Generate Domain. Jika port diminta, sesuaikan dengan PORT bot.
Kode ini memakai callback default merchant TriPay. Tidak perlu menambahkan variabel callback URL di Railway.
Pastikan callback dapat diakses publik. Membuka URL callback lewat browser adalah GET dan tidak membuktikan callback POST gagal/berhasil; gunakan Callback Tester atau transaksi Sandbox untuk pengujian.
Simpan API Key dan Private Key hanya di Variables Railway, bukan melalui chat atau repository.

DUA PEMBAYARAN
/shop > Beli OTP > Aplikasi > Negara > Operator > Produk > pilih pembayaran.
1. Bayar Pakai Saldo: saldo bot dipotong harga jual; pesanan dibuat di SMSCode.
2. Bayar Langsung QRIS: pembeli mengisi email tagihan, lalu memindai QRIS TriPay. Tidak perlu saldo bot. Pesanan dibuat otomatis setelah status PAID dibaca dari API TriPay.
Untuk QRIS, harga produk minimal 1.000 IDR, maksimal batas aplikasi 1.000.000 IDR; untuk produk di bawah 1.000 gunakan saldo. QR berlaku 20 menit sesuai request; provider tetap menentukan status akhir.
Bot menampilkan harga produk, biaya QRIS pembeli, dan total bayar. Biaya mengikuti pengaturan merchant TriPay. Jika biaya ditanggung merchant, total pembeli sama dengan harga produk tetapi dana bersih merchant berkurang. Jika ditanggung pembeli, total bayar bertambah; nominal saldo/produk tetap sebesar harga awal, bukan total termasuk biaya.
Biaya standar QRIS pada dokumentasi TriPay adalah Rp750 + 0,7%, tetapi akun merchant dapat mempunyai biaya berbeda. Periksa pengaturan biaya merchant agar sesuai keuntungan toko.
Saldo SMSCode adalah dana terpisah dari saldo akun TriPay; admin tetap perlu memastikan saldo provider cukup untuk membuat pesanan. Pembayaran QRIS tidak mengisi saldo SMSCode secara otomatis.

ISI SALDO QRIS
/shop > Isi Saldo > QRIS Otomatis > masukkan nominal 5.000–1.000.000 dan email > bayar QR > saldo bot bertambah satu kali setelah terverifikasi.
Riwayat Isi Saldo terpisah dari Riwayat QRIS Beli.

HASIL DAN KEGAGALAN PEMBELIAN
Setelah QRIS dibayar, nomor pesanan tersedia lewat Cek Pembayaran & Pesanan pada pesan tagihan. Riwayat QRIS Beli tersedia untuk admin melalui /admin. Bot juga mencoba mengirim hasil melalui DM. Jika DM ditutup, pembeli dapat memakai tombol Cek Pembayaran & Pesanan pada pesan tagihan atau meminta admin memeriksa riwayat. Cek OTP dan Batalkan tersedia untuk pesanan berhasil.
Stok tidak dipesan sebelum pembayaran. Jika habis/nonaktif atau harga dasar berubah, harga produk dikembalikan sekali ke SALDO BOT, bukan rekening pembayaran. Biaya QRIS tidak dikembalikan otomatis. Kebijakan ini ditampilkan pada QRIS pembelian.
Jika koneksi ke SMSCode terputus setelah permintaan order, hasil mungkin belum pasti. Bot menandainya review dan tidak membeli ulang otomatis. Admin dapat melihat /admin > Transaksi > Pembayaran Perlu Diperiksa dan mencocokkan tagihan dengan riwayat SMSCode sebelum menyelesaikan/mengganti dana. Tombol resolusi tersedia melalui /admin > Transaksi > Pembayaran Perlu Diperiksa; ikuti panduan lima fitur di atas.
Tagihan yang tidak menampilkan QR setelah respons terputus tetap disimpan. Jangan langsung membuat QR lain; minta admin mengecek riwayat/callback dan mencocokkan merchant_ref pada TriPay. Callback yang valid bisa memulihkan referensi TriPay yang belum tersimpan.

VERIFIKASI DAN PEMULIHAN
Callback memakai HMAC-SHA256 dari byte body asli dan Private Key, serta event payment_status. Status dibaca ulang dari /transaction/detail. Referensi, merchant_ref, channel, harga item, biaya dan total bayar diperiksa. Respons callback berhasil adalah {success:true}.
Notifikasi berulang tidak menggandakan saldo/pesanan. Pemeriksaan setiap 30 detik memproses maksimal 5 tagihan per putaran; keterlambatan API dapat menambah waktu. Proses provider yang terputus saat restart ditandai review, bukan dibeli ulang.
Tagihan Midtrans lama tetap disimpan; integrasi TriPay tidak memprosesnya. Jika ada tagihan Midtrans lama yang terbayar/tertunda, admin perlu memeriksanya di Midtrans sebelum menyelesaikan secara manual. Penggantian mode Sandbox/Production juga tidak mengubah mode tagihan lama. Jangan mencampur credential/mode.

ADMIN DAN HARGA
ADMIN_DISCORD_IDS berisi ID pengguna admin Discord, beberapa ID dipisahkan koma. DISCORD_CLIENT_ID wajib untuk registrasi /shop dan /admin.
/admin > Katalog > Katalog Provider > Aplikasi > Negara > Operator > Produk menampilkan harga dasar, harga jual, selisih, stok dan status. Katalog dibaca SMSCode, cache 60 detik, pilihan memakai tombol dengan navigasi.
Atur Harga Jual berlaku global: harga dasar + pembulatan ke atas(harga dasar x persen/100) + tambahan rupiah. Contoh dasar 5.000, markup 20%, tambahan 0 = jual 6.000 IDR. Default markup 0 sampai diatur. Harga dasar provider tidak dapat diubah dari bot. Produk Manual adalah katalog terpisah, tidak dipakai oleh Beli OTP.

PENYIMPANAN DAN TES
Gunakan satu instance bot dan shop.db pada volume persisten supaya saldo, tagihan, pesanan serta pengaturan harga tetap ada saat redeploy.
51 tes lokal menggunakan mock provider lulus. Menjalankan tes:
node --test catalog.test.js admin.test.js purchase-flow.test.js payments.test.js commerce.test.js direct-payments.test.js
Tes SQLite dijalankan dengan Node 24; aplikasi bot memakai better-sqlite3 dari package.json dan Node 22. Belum diuji langsung menggunakan akun TriPay/Discord/SMSCode pengguna. Uji Sandbox dan callback sebelum mengaktifkan Production.
